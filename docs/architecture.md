# Архитектура и обоснование решений

Этот документ отвечает на вопросы вида «почему именно так», которые обычно
задают на защите.

## 1. Почему обработка асинхронная, а не «загрузил → сразу получил ответ»?

Инференс нейросети занимает 1–3 секунды на CPU (больше при холодном старте).
Если делать синхронно:

- HTTP-воркеры API заняты ожиданием — при 50 одновременных загрузках API
  перестаёт отвечать даже на `/health`;
- нет буфера: всплеск нагрузки = отказы;
- падение ML-сервиса = потеря запросов;
- нельзя масштабировать обработку отдельно от API.

С очередью: API отвечает за миллисекунды (`202 Accepted`), задачи ждут в Kafka,
воркеров можно добавить `docker compose up --scale worker=5`, а падение ML
означает только задержку, не потерю данных.

## 2. Почему Kafka, а не Redis-очередь / RabbitMQ / горутина с каналом?

| Вариант              | Проблема для нашей задачи |
|----------------------|---------------------------|
| Канал в процессе API | задачи теряются при рестарте; нельзя вынести воркер отдельно |
| Redis LIST / Streams | подходит, но нет consumer groups с партиционированием в LIST; Streams — ок, но Kafka изучалась в курсе и лучше масштабируется |
| RabbitMQ             | тоже подходит; выбрана Kafka как индустриальный стандарт для событий и из-за программы курса |

Используем Kafka как **шину событий**, а не RPC: API публикует факт
«изображение загружено», и его не интересует, кто и когда это обработает
(хореография). Это позволяет позже добавить второго консьюмера (например,
модерацию контента) без изменения API.

Ключ сообщения — `user_id`: события одного пользователя попадают в одну
партицию и обрабатываются по порядку.

## 3. Гарантии доставки и идемпотентность

- Оффсет коммитится **после** успешной записи результата → at-least-once.
- Значит, сообщение может прийти дважды (например, воркер упал между записью в
  БД и коммитом). Поэтому первое действие воркера —
  `UPDATE analyses SET status='processing' WHERE id=$1 AND status IN ('pending','processing')`.
  Если `RowsAffected = 0` — анализ уже `done`/`failed`/удалён, сообщение
  пропускается.
- Ошибки делятся на два класса:
  - **инфраструктурные** (недоступен Postgres/MinIO) → `Handle` возвращает
    ошибку, оффсет не коммитится, Kafka перечитает сообщение;
  - **ошибки обработки** (ML вернул ошибку) → ретраи внутри воркера с
    экспоненциальной задержкой (2s, 4s, 8s), затем `failed` + событие в DLQ
    `image.failed`, сообщение коммитится. Иначе одно «ядовитое» сообщение
    заблокировало бы партицию навсегда.
- Битое изображение (`InvalidArgument` от ML) не ретраится вообще.

## 4. Почему Redis, если есть Postgres?

Три разных задачи, где нужна скорость, а не долговечность:

1. **Статусы задач.** Клиент опрашивает `GET /analyses/{id}` каждую секунду. Это
   самый частый запрос в системе; отдавать его из Postgres — значит нагружать
   основную БД бессмысленными чтениями. В Redis статус с TTL 24 часа; при
   промахе — fallback в Postgres и прогрев кэша.
2. **Статистика.** `GROUP BY dominant` по истории пользователя — тяжёлый
   запрос; кэшируем на 5 минут и инвалидируем при завершении анализа.
3. **Rate limiting.** `INCR` + `EXPIRE` — атомарный счётчик по окну в минуту.
   Работает одинаково для нескольких реплик API, в отличие от in-memory
   лимитера.

Redis **не источник истины**: его можно очистить, и система продолжит работать
(чуть медленнее).

## 5. Почему MinIO, а не bytea в Postgres или файл на диске?

- `bytea` раздувает таблицы, WAL и бэкапы; Postgres плохо подходит для блобов
  по 1–10 МБ.
- Локальный диск не разделяется между контейнерами API и воркера, и исчезает
  при пересоздании контейнера.
- MinIO реализует S3 API: в проде заменяется на AWS S3 / Yandex Object Storage
  сменой адреса и ключей, код не меняется.

## 6. Почему gRPC между воркером и ML, а не HTTP/JSON?

- **Типизированный контракт** в `.proto`: Go и Python генерируют код из одного
  файла, несовместимость ловится при компиляции.
- **Бинарная передача** изображения без base64 (+33 % к размеру в JSON).
- **Стандартные коды ошибок**: `InvalidArgument` → не ретраить,
  `Unavailable`/`DeadlineExceeded` → ретраить.
- Это ровно тот случай, для которого gRPC создавался: внутреннее
  взаимодействие сервисов с высокой частотой вызовов.

Наружу (клиентам) остаётся REST: браузерам и мобильным приложениям так проще.

## 7. Почему ML на Python, а не на Go?

Распознавание эмоций — готовая предобученная нейросеть. Экосистема обучения
и инференса (TensorFlow, PyTorch, DeepFace) живёт в Python; на Go нет зрелых
аналогов, а обёртки над C-библиотеками сложны в сборке и поддержке.

Поэтому ML — **тонкий сервис** (~100 строк), который делает одно: байты →
распределение эмоций. Вся логика — приём, хранение, очередь, ретраи, статусы,
безопасность, статистика — на Go. Это типичное разделение ответственности в
индустрии: ML-команда отдаёт модель как сервис, бэкенд-команда строит вокруг
неё продукт.

Go-код зависит от интерфейса `mlclient.Analyzer`, а не от gRPC: при желании
можно подставить облачный Vision API, написав одну реализацию.

## 8. Слоистая архитектура

```
transport (HTTP / Kafka)  →  service  →  repository / storage / mlclient
          ↓                     ↓                ↓
        dto                  domain         Postgres / Redis / MinIO / gRPC
```

- `transport` парсит вход, вызывает сервис, формирует ответ. Не знает про SQL.
- `service` — бизнес-правила. Зависит только от интерфейсов из `ports.go`.
  Не знает ни про HTTP, ни про pgx.
- `repository` — SQL. Возвращает доменные сущности и «технические» ошибки
  (`ErrNotFound`, `ErrConflict`), которые сервис переводит в `apperror`.
- `domain` — чистые структуры без тегов JSON/SQL. `dto` — отдельно, потому что
  контракт API и внутренняя модель меняются по разным причинам.

Зависимости направлены внутрь → сервисный слой тестируется in-memory моками
(см. `internal/service/mocks_test.go`), без Docker.

## 9. Обработка ошибок

Один тип `apperror.Error{Code, Message, Err, Details}`:

- сервисы возвращают `apperror.NotFound(...)`, `apperror.Conflict(...)` и т. д.;
- хендлеры делают `c.Error(err)` и выходят;
- middleware `ErrorHandler` переводит код в HTTP-статус и JSON.

Внутренние причины (`Err`) логируются, но клиенту не отдаются: в ответе не
окажется DSN базы или stack trace. Ошибки валидации приходят с `details`
по полям.

## 10. Аутентификация

- Пароли — bcrypt (cost 12).
- Access-токен — JWT HS256, 15 минут, содержит `uid` и `role`. Проверяется
  без обращения к БД (stateless).
- Refresh-токен — случайные 32 байта, в БД хранится только SHA-256-хеш,
  7 дней. При обновлении **ротируется**: старый удаляется. `logout` удаляет
  все refresh-токены пользователя.
- Роли проверяются middleware `RequireRole`; админские эндпоинты — `/admin/*`.
- Сообщение об ошибке входа одинаково для «нет такого email» и «неверный
  пароль», чтобы не раскрывать базу пользователей.

## 11. Graceful shutdown

Оба бинарника используют `signal.NotifyContext`:

- **API**: `http.Server.Shutdown` с таймаутом 10 с — активные запросы
  дорабатывают, новые не принимаются. Docker посылает SIGTERM и ждёт
  10 с до SIGKILL — укладываемся.
- **Worker**: отмена контекста останавливает `FetchMessage`; горутины,
  обрабатывающие текущие сообщения, видят `ctx.Err()`, возвращают анализ в
  `pending` и выходят. Оффсет не коммитится → после рестарта сообщение
  перечитается.

## 12. Конфигурация и окружения

Всё через переменные окружения (12-factor). `APP_ENV`:

- `dev` — читается `.env`, текстовые логи, дефолтный JWT-секрет;
- `stage`/`prod` — JSON-логи, `JWT_SECRET` обязателен, `gin.ReleaseMode`.

Конфиг валидируется при старте: лучше упасть сразу с понятной ошибкой, чем
через час в проде.

## 13. Миграции

SQL-файлы `NNNN_name.up.sql` / `.down.sql` в `migrations/`, совместимы с
`golang-migrate`. Они же встраиваются в бинарник через `embed` и применяются
при старте API (`POSTGRES_MIGRATE_ON_START=true`), так что `docker compose up`
даёт рабочую систему без ручных шагов. В проде обычно миграции запускают
отдельным шагом деплоя — для этого есть `make migrate-up`.

## 14. Что бы я сделал дальше

- Outbox-паттерн: сейчас запись в Postgres и публикация в Kafka — два действия;
  если Kafka недоступна, анализ помечается `failed`. Outbox сделал бы это
  атомарным.
- Метрики Prometheus (латентность инференса, глубина очереди, ошибки).
- Трассировка OpenTelemetry через request-id → Kafka headers → gRPC metadata.
- WebSocket/SSE вместо опроса статуса.
